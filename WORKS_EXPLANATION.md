# Объяснение практических работ

Этот файл можно использовать как шпаргалку перед объяснением работ преподавателю. Основная тема проекта, начиная со второй работы, - **тайм-трекер**, то есть консольное C++ приложение для учета рабочего времени по задачам.

## Практическая работа 1: минимальный C++ проект

Папка: `KR1`

### Что сделано

В первой работе подготовлен минимальный C++ проект, который выводит `Hello, World!`. Код разделен на несколько файлов:

- `main.cpp` - точка входа программы;
- `hello.h` - объявление функции `printHelloWorld`;
- `hello.cpp` - реализация функции `printHelloWorld`;
- `Makefile` - сборка проекта через `make`;
- `README.md` - краткое описание структуры и запуска.

### Как объяснять

Главная идея работы - показать базовую организацию C++ проекта не в одном файле, а с разделением объявления и реализации. В `hello.h` находится интерфейс функции, в `hello.cpp` - ее тело, а `main.cpp` только вызывает готовую функцию.

Такой подход нужен, чтобы проект можно было расширять: отдельные модули подключаются через заголовочные файлы, а реализация хранится в `.cpp`.

### Что показать преподавателю

Можно открыть `main.cpp` и сказать:

> Здесь находится точка входа. Она подключает `hello.h` и вызывает функцию вывода.

Затем открыть `hello.h` и `hello.cpp`:

> Заголовочный файл содержит объявление функции, а исходный файл содержит реализацию.

В `Makefile` можно показать, что сборка выполняется командой `make`, а запуск - командой `make run`.

## Практическая работа 2: выбор темы, требования, SRS и UML

Папка: `KR2`

### Что сделано

Во второй работе выбрана тема проекта: **тайм-трекер**. Это консольное приложение для учета рабочего времени по задачам.

Подготовлены документы:

- `requirements.md` - сбор и классификация требований;
- `srs.md` - спецификация требований к программному обеспечению;
- `report.html` - оформленная версия отчета с титульным листом и UML-диаграммами;
- `report.pdf` - PDF-версия для сдачи;
- `README.md` - описание состава работы.

### Почему выбрана тема тайм-трекера

Тема удобна для учебного проекта, потому что:

- предметная область простая и понятная;
- не нужны сеть, графический интерфейс и внешние API;
- приложение можно реализовать как консольную программу на C++;
- требования легко описать через пользовательские сценарии.

### Основные требования

В проекте описаны функции:

- создание задач;
- просмотр списка задач;
- запуск таймера по выбранной задаче;
- остановка активного таймера;
- просмотр истории рабочих сессий;
- формирование отчета;
- сохранение и загрузка данных.

### Как объяснять SRS

SRS - это документ, который фиксирует, что должна делать система. В нем есть:

- цель проекта;
- область действия;
- определения: задача, сессия, отчет;
- функциональные требования;
- нефункциональные требования;
- UML-диаграммы.

Можно сказать:

> Во второй работе я не писал основную реализацию приложения, а формализовал будущую систему: выбрал тему, описал пользователей, функции, ограничения и основные классы.

### UML-диаграммы

В `report.html` есть:

- диаграмма вариантов использования - показывает, что пользователь может делать в системе;
- диаграмма классов - показывает основные сущности проекта;
- диаграмма последовательности - показывает сценарий запуска и остановки таймера.

## Практическая работа 3: паттерны проектирования и CMake

Папка: `KR3`

### Что сделано

В третьей работе проект был превращен в модульное C++ приложение. Добавлены:

- каталог `include/` с заголовочными файлами;
- каталог `src/` с реализациями;
- `CMakeLists.txt` для сборки через CMake;
- `README.md` с инструкциями;
- `report.html` и `report.pdf` с главой о паттернах проектирования.

### Структура проекта

Основные классы:

- `Task` - модель задачи;
- `TimeSession` - модель рабочей сессии;
- `TaskManager` - создание, поиск и архивирование задач;
- `TimeTracker` - запуск и остановка таймера;
- `Storage` - сохранение и загрузка данных;
- `ReportService` - расчет суммарного времени;
- `ConsoleUI` - консольное меню.

### Как работает программа

При запуске `main.cpp` создает основные объекты:

1. `TaskManager` хранит задачи.
2. `Storage` загружает сохраненные задачи из файлов.
3. `TimeTracker` отвечает за рабочие сессии.
4. `ConsoleUI` запускает меню пользователя.

Пользователь через меню может добавить задачу, запустить таймер, остановить его, посмотреть историю и отчет.

### CMake

Файл `CMakeLists.txt` задает:

- минимальную версию CMake;
- имя проекта;
- стандарт C++17;
- исполняемый файл `time_tracker`;
- список `.cpp` файлов;
- путь к заголовкам `include/`.

Команды сборки:

```sh
cmake -S . -B build
cmake --build build
```

### Паттерны проектирования

В отчете описаны применимые паттерны:

- **Facade** - `ConsoleUI` скрывает работу нескольких подсистем за простым меню.
- **Repository** - `Storage` отделяет бизнес-логику от хранения данных в файлах.
- **Singleton** - может быть использован для будущего класса конфигурации `AppConfig`.
- **Strategy** - может быть использован для разных видов отчетов.
- **Command** - может быть использован для пунктов меню как отдельных команд.
- **Factory Method** - может быть использован для создания сессий и отчетов.

### Что важно сказать про паттерны

Не все паттерны обязательно реализованы в коде полностью. В работе требовалось описать, какие паттерны применимы к проекту и почему. Поэтому часть паттернов уже видна в архитектуре, например `Facade` и `Repository`, а часть описана как направление развития проекта.

## Практическая работа 4: тестирование проекта

Папка: `KR4`

### Что сделано

В четвертой работе к проекту добавлена система тестирования на Catch2.

Добавлены:

- `tests/CMakeLists.txt` - подключение Catch2 и сборка тестов;
- unit-тесты для основных классов;
- отдельные мини-программы сценариев;
- `TEST_SCENARIOS.md` - описание сценариев;
- обновленный `README.md`;
- `report.html` и `report.pdf` с отчетом по тестированию.

### Как подключены тесты

В корневом `CMakeLists.txt` основная логика проекта вынесена в библиотеку `time_tracker_lib`. Это нужно, чтобы и основное приложение, и тесты могли использовать одни и те же классы.

Схема такая:

- `time_tracker_lib` содержит основную логику;
- `time_tracker` - основная программа, которая линкуется с `time_tracker_lib`;
- `unit_tests` - тестовая программа, которая тоже линкуется с `time_tracker_lib`;
- Catch2 подключается через `FetchContent`.

### Unit-тесты

Тесты находятся в папке `KR4/tests`.

Что проверяется:

- `test_task.cpp` - статусы задач и модель `Task`;
- `test_time_session.cpp` - расчет длительности сессии;
- `test_task_manager.cpp` - добавление, поиск и архивирование задач;
- `test_time_tracker.cpp` - запуск и остановка таймера;
- `test_storage.cpp` - сохранение и загрузка данных;
- `test_report_service.cpp` - расчет и вывод отчета;
- `test_console_ui.cpp` - работа консольного меню через подмену `std::cin` и `std::cout`.

### Тестовые сценарии

Кроме unit-тестов есть отдельные мини-программы в `tests/scenarios`:

- `scenario_basic_workflow.cpp` - создать задачу, запустить таймер, остановить таймер;
- `scenario_persistence.cpp` - сохранить данные и загрузить их повторно;
- `scenario_reporting.cpp` - сформировать отчет по нескольким задачам.

Эти программы показывают не отдельные функции, а цельные пользовательские процессы.

### Как запускать тесты

Команды:

```sh
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
```

После сборки unit-тесты находятся в `build/tests/unit_tests`, а сценарии - в `build/tests/scenarios`.

На текущей машине во время подготовки `cmake` не был найден в `PATH`, поэтому тесты не запускались локально через CMake. Но проект настроен так, что после установки CMake и компилятора тесты должны собираться стандартными командами из `README.md`.

## Возможные вопросы преподавателя

### Почему проект разделен на `include` и `src`?

`include` содержит заголовочные файлы, то есть интерфейсы классов. `src` содержит реализации. Такое разделение принято в C++ проектах и упрощает сборку, чтение и расширение кода.

### Зачем нужен `TaskManager`?

Он отвечает за работу с задачами: создает задачи, ищет их по идентификатору, архивирует и хранит список задач. Благодаря этому логика задач не смешивается с интерфейсом и хранением файлов.

### Зачем нужен `TimeTracker`?

Он отвечает за рабочие сессии: запускает таймер, останавливает его и следит, чтобы одновременно была только одна активная сессия.

### Зачем нужен `Storage`?

Он изолирует сохранение и загрузку данных. Остальные классы не знают, как именно данные лежат в файлах. Это похоже на паттерн Repository.

### Почему выбран Catch2?

Catch2 удобно подключается к CMake, позволяет писать короткие и читаемые тесты и хорошо подходит для учебных C++ проектов.

### Чем unit-тесты отличаются от сценариев?

Unit-тест проверяет маленькую часть программы, например один класс или одну функцию. Сценарий проверяет полный пользовательский процесс: создать задачу, запустить таймер, остановить таймер, сохранить данные или сформировать отчет.
