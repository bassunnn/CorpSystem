# Объяснение контрольной работы 4

Проект: **тайм-трекер** - консольное C++ приложение для учета рабочего времени по задачам.

Главная идея четвертой работы: добавить к проекту систему тестирования. В третьей работе была сделана модульная структура приложения, а в четвертой проверяется, что эти модули работают правильно. Для unit-тестов используется библиотека **Catch2**, а сборка и запуск тестов подключены через **CMake** и **CTest**.

## Что сказать в начале

В этой работе я добавил автоматические тесты для основных классов проекта. Тесты проверяют модели данных, управление задачами, запуск и остановку таймера, сохранение в файлы, формирование отчетов и работу консольного интерфейса.

Также проект был немного перестроен: основная логика вынесена в библиотеку `time_tracker_lib`, чтобы ее можно было подключать и к приложению, и к тестам.

## Для чего нужны папки и файлы

`include/` - заголовочные файлы классов. Здесь объявлены структуры, классы и методы.

`src/` - реализация приложения. Здесь находится код методов и `main.cpp`.

`tests/` - unit-тесты Catch2. Каждый файл проверяет отдельный модуль проекта.

`tests/scenarios/` - отдельные мини-программы со сценариями. Они проверяют не одну функцию, а целый пользовательский процесс.

`TEST_SCENARIOS.md` - текстовое описание тестовых сценариев: какие шаги выполняются и какой результат ожидается.

`CMakeLists.txt` - основной файл сборки. Он собирает библиотеку, приложение и подключает тесты.

`tests/CMakeLists.txt` - файл сборки тестов. Он скачивает Catch2, собирает unit-тесты и сценарные программы.

`report.html` и `report.pdf` - отчет по четвертой работе.

## Как собираются тесты

В `tests/CMakeLists.txt` используется `FetchContent`.

Он нужен, чтобы CMake сам скачал Catch2 из GitHub:

```text
GIT_REPOSITORY https://github.com/catchorg/Catch2.git
GIT_TAG v3.5.3
```

После этого создается исполняемый файл:

```text
unit_tests
```

Он собирается из файлов:

- `test_task.cpp`;
- `test_time_session.cpp`;
- `test_task_manager.cpp`;
- `test_time_tracker.cpp`;
- `test_storage.cpp`;
- `test_report_service.cpp`;
- `test_console_ui.cpp`.

Команда:

```text
add_test(NAME unit_tests COMMAND unit_tests)
```

регистрирует тесты в CTest. Благодаря этому их можно запускать командой:

```sh
ctest --test-dir build --output-on-failure
```

## Команды сборки и запуска тестов

```sh
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
```

Что сказать: первая команда настраивает проект, вторая собирает приложение и тесты, третья запускает тесты.

## Unit-тесты

### `test_task.cpp`

Проверяет модель задачи и статусы.

Что проверяется:

- статус задачи можно перевести в строку;
- строку можно перевести обратно в `TaskStatus`;
- активная и архивная задача различаются.

Зачем нужно: задача - базовая модель проекта, поэтому важно, чтобы ее состояние корректно сохранялось и загружалось.

### `test_time_session.cpp`

Проверяет рабочую сессию.

Что проверяется:

- длительность завершенной сессии считается правильно;
- активная сессия считает длительность до текущего момента.

Зачем нужно: тайм-трекер основан на подсчете времени, поэтому расчет длительности должен быть надежным.

### `test_task_manager.cpp`

Проверяет `TaskManager`.

Что проверяется:

- создание задачи;
- генерация `id`;
- поиск задачи по номеру;
- архивирование задачи;
- замена списка задач загруженными данными.

Зачем нужно: `TaskManager` отвечает за список задач, и ошибка в нем сломает основную работу приложения.

### `test_time_tracker.cpp`

Проверяет `TimeTracker`.

Что проверяется:

- запуск таймера по активной задаче;
- запрет запуска таймера по несуществующей задаче;
- запрет запуска таймера по архивной задаче;
- запрет второго активного таймера;
- остановка активной сессии.

Зачем нужно: это основная логика тайм-трекера.

### `test_storage.cpp`

Проверяет `Storage`.

Что проверяется:

- сохранение задач в файл;
- загрузка задач из файла;
- сохранение рабочих сессий;
- загрузка рабочих сессий;
- корректность данных после повторной загрузки.

Зачем нужно: приложение хранит данные в CSV, поэтому нужно убедиться, что после закрытия и открытия информация не теряется.

### `test_report_service.cpp`

Проверяет `ReportService`.

Что проверяется:

- суммарное время группируется по задачам;
- активные сессии не попадают в итоговый отчет;
- печать отчета работает без ошибки.

Зачем нужно: отчет должен показывать только завершенное рабочее время.

### `test_console_ui.cpp`

Проверяет `ConsoleUI`.

Что проверяется:

- работа меню через подмену консольного ввода;
- добавление задачи через интерфейс;
- вывод списка задач;
- сохранение данных при выходе.

Зачем нужно: даже если внутренние классы работают правильно, нужно проверить, что пользовательское меню вызывает их корректно.

## Сценарные тесты

Сценарные тесты находятся в `tests/scenarios/`. Это не Catch2-тесты, а отдельные маленькие программы. Они проверяют полный процесс.

### `scenario_basic_workflow.cpp`

Проверяет базовый рабочий процесс:

1. создать задачу;
2. запустить таймер;
3. остановить таймер;
4. убедиться, что сессия создана и завершена.

Ожидаемый результат: программа выводит `Basic workflow passed`.

### `scenario_persistence.cpp`

Проверяет сохранение и загрузку:

1. создать временное хранилище;
2. сохранить задачу и рабочую сессию;
3. загрузить данные повторно;
4. убедиться, что данные совпадают.

Ожидаемый результат: программа выводит `Persistence scenario passed`.

### `scenario_reporting.cpp`

Проверяет формирование отчета:

1. создать несколько задач;
2. добавить рабочие сессии;
3. рассчитать суммарное время;
4. вывести отчет.

Ожидаемый результат: программа выводит отчет и `Reporting scenario passed`.

## Как данные проходят через тесты

Пример теста `TaskManager`:

1. Создается объект `TaskManager`.
2. Вызывается `addTask`.
3. Проверяется, что задача появилась в списке.
4. Вызывается `archiveTask`.
5. Проверяется, что статус стал `Archived`.

Пример теста `TimeTracker`:

1. Создается задача через `TaskManager`.
2. Создается `TimeTracker`.
3. Запускается таймер по `id` задачи.
4. Проверяется наличие активной сессии.
5. Таймер останавливается.
6. Проверяется, что активной сессии больше нет.

Пример теста `Storage`:

1. Создается временная папка.
2. В нее сохраняются задачи или сессии.
3. Данные загружаются обратно.
4. Проверяется количество и значения полей.

## Почему тесты важны

Тесты нужны, чтобы автоматически проверять проект после изменений. Если случайно сломать расчет времени, сохранение или меню, тесты покажут ошибку.

Unit-тесты проверяют маленькие части программы отдельно.

Сценарные тесты проверяют, что несколько модулей работают вместе.

## Возможные вопросы и ответы

**Что такое Catch2?**

Catch2 - это библиотека для unit-тестирования C++. Она позволяет писать тестовые случаи и проверки через `REQUIRE` или похожие макросы.

**Зачем нужен CTest?**

CTest - это инструмент CMake для запуска тестов. Он позволяет запускать все зарегистрированные тесты одной командой.

**Зачем основной код вынесен в библиотеку?**

Чтобы тесты могли подключать те же классы, что и основное приложение. Иначе пришлось бы дублировать код или тестировать только через готовый исполняемый файл.

**Чем unit-тесты отличаются от сценарных тестов?**

Unit-тест проверяет маленький модуль или функцию. Сценарный тест проверяет цепочку действий, похожую на реальное использование программы.

**Что проверяет `test_storage.cpp`?**

Он проверяет, что задачи и рабочие сессии корректно сохраняются в CSV-файлы и загружаются обратно.

**Что будет, если тест упадет?**

CTest покажет ошибку. Если запускать тесты в автоматической сборке, сборку можно считать неуспешной.

**Почему активные сессии не учитываются в отчете?**

Потому что у активной сессии еще нет окончательного времени завершения, а отчет должен показывать завершенную работу.
