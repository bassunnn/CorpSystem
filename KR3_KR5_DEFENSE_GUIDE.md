# Шпаргалка для объяснения KR3-KR5

Проект во всех трех работах один: **тайм-трекер** - консольное C++ приложение для учета рабочего времени по задачам.

Главная линия развития:

```text
KR3 - модульная архитектура приложения
KR4 - автоматическое тестирование
KR5 - контейнеризация через Docker
```

## Коротко обо всех работах

### KR3

В `KR3` проект превращается в нормальное модульное C++ приложение.

Что важно сказать:

> В третьей работе я разделил приложение на модули. В `include` находятся заголовочные файлы, в `src` - реализации. Каждый класс отвечает за свою часть: задачи, рабочие сессии, таймер, хранение, отчеты и консольное меню. Проект собирается через CMake.

Главная тема: **структура проекта и разделение ответственности**.

### KR4

В `KR4` к проекту добавлены тесты.

Что важно сказать:

> В четвертой работе я добавил unit-тесты на Catch2 и сценарные тесты. Основная логика вынесена в библиотеку `time_tracker_lib`, чтобы ее можно было подключать и к приложению, и к тестам. Тесты запускаются через CTest.

Главная тема: **проверка корректности программы**.

### KR5

В `KR5` проект упакован в Docker.

Что важно сказать:

> В пятой работе я добавил Dockerfile с многостадийной сборкой. На стадии `build` проект собирается и проходят тесты, а в финальный runtime-образ копируется только готовая программа. Также добавлен запуск через аргументы командной строки, чтобы приложением было удобно пользоваться в контейнере.

Главная тема: **запуск проекта в чистом Linux-окружении**.

## Как объяснить связь между KR3, KR4 и KR5

Можно сказать так:

> Эти работы идут последовательно. В KR3 я сделал архитектуру приложения. В KR4 я добавил тестирование этой архитектуры. В KR5 я упаковал уже протестированный проект в Docker, чтобы его можно было собрать и запустить на любой машине без ручной настройки окружения.

То есть:

- `KR3` отвечает на вопрос: **как устроена программа?**
- `KR4` отвечает на вопрос: **как проверить, что программа работает правильно?**
- `KR5` отвечает на вопрос: **как запустить программу в одинаковом окружении?**

### `include/`

Здесь лежат заголовочные файлы. Они описывают интерфейс классов: какие методы есть, какие данные хранит объект, какие функции доступны другим частям программы.

Файлы:

- `Task.h` - модель задачи;
- `TimeSession.h` - модель рабочей сессии;
- `TaskManager.h` - управление задачами;
- `TimeTracker.h` - запуск и остановка таймера;
- `Storage.h` - загрузка и сохранение данных;
- `ReportService.h` - отчеты;
- `ConsoleUI.h` - консольное меню.

### `src/`

Здесь лежат реализации. То есть в `.h` написано, что умеет класс, а в `.cpp` написано, как именно он это делает.

### `data/`

Здесь хранятся данные приложения:

- `tasks.csv` - задачи;
- `sessions.csv` - рабочие сессии.

### `CMakeLists.txt`

Файл сборки. Он указывает:

- стандарт C++17;
- имя проекта;
- какие `.cpp` файлы надо собрать;
- где искать заголовочные файлы.

## KR3: основные классы

### `Task`

Описывает одну задачу.

Поля:

- `id` - номер задачи;
- `title` - название;
- `description` - описание;
- `status` - статус задачи.

Статусы:

- `Active` - активная задача;
- `Archived` - архивная задача.

### `TimeSession`

Описывает один промежуток работы над задачей.

Поля:

- `id` - номер сессии;
- `taskId` - к какой задаче относится;
- `startTime` - время начала;
- `endTime` - время окончания;
- `active` - идет ли сессия сейчас.

Главная функция:

- `durationSeconds()` - считает длительность сессии.

### `TaskManager`

Управляет списком задач.

Основные функции:

- `addTask` - добавить задачу;
- `archiveTask` - архивировать задачу;
- `findTask` - найти задачу;
- `tasks` - получить список задач;
- `replaceTasks` - заменить список задач загруженными из файла.

### `TimeTracker`

Управляет таймером и рабочими сессиями.

Основные функции:

- `start` - запустить таймер по задаче;
- `stop` - остановить активный таймер;
- `activeSession` - найти активную сессию;
- `sessions` - получить историю сессий.

Важно: нельзя запустить таймер по несуществующей или архивной задаче.

### `Storage`

Сохраняет и загружает данные из CSV.

Основные функции:

- `loadTasks`;
- `saveTasks`;
- `loadSessions`;
- `saveSessions`.

Можно сказать, что это простой вариант паттерна **Repository**.

### `ReportService`

Считает отчет по времени.

Основные функции:

- `totalSecondsByTask` - суммарное время по задачам;
- `printReport` - печать отчета.

### `ConsoleUI`

Консольное меню пользователя.

Пункты меню:

- добавить задачу;
- посмотреть список задач;
- архивировать задачу;
- запустить таймер;
- остановить таймер;
- показать историю;
- показать отчет;
- сохранить и выйти.

Можно сказать, что это простой вариант паттерна **Facade**, потому что `ConsoleUI` скрывает работу нескольких классов за одним меню.

## KR4: что добавилось

В `KR4` структура проекта почти такая же, но добавилась папка:

```text
tests/
```

И изменился основной `CMakeLists.txt`: теперь основная логика собирается в библиотеку:

```text
time_tracker_lib
```

Зачем это нужно:

> Если весь код сразу собрать только в исполняемый файл, тестам неудобно подключаться к внутренним классам. Поэтому логика вынесена в библиотеку, а потом эта библиотека подключается и к приложению, и к тестам.

## KR4: Catch2, CMake и CTest

В `tests/CMakeLists.txt` используется `FetchContent`.

Он скачивает Catch2:

```text
https://github.com/catchorg/Catch2.git
```

Потом собирается исполняемый файл:

```text
unit_tests
```

А команда:

```text
add_test(NAME unit_tests COMMAND unit_tests)
```

регистрирует тесты в CTest.

Команды запуска:

```sh
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
```

Если на Windows нет CMake, тесты можно запускать через Docker.

## KR5: Dockerfile

Dockerfile использует многостадийную сборку:

```text
build
runtime
```

### Стадия `build`

На этой стадии устанавливаются:

- `cmake`;
- `g++`;
- `git`;
- `make`;
- `ca-certificates`.

Потом выполняется:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

То есть проект не просто собирается, но и тестируется.

### Стадия `runtime`

В финальный образ копируется только готовый бинарный файл:

```text
/usr/local/bin/time_tracker
```

Исходники, временные файлы сборки и Catch2 в финальный образ не попадают.

## KR5: зачем нужен `.dockerignore`

`.dockerignore` нужен, чтобы не отправлять в Docker лишние файлы:

- `.git`;
- папки `build`;
- временные файлы CMake;
- `.exe`;
- `.dll`;
- локальные CSV-файлы.

Это делает сборку чище.

## KR5: где хранятся данные

Внутри контейнера данные находятся в:

```text
/app/data
```

Если запускать контейнер с `--rm` без volume, данные пропадут после завершения контейнера.

Чтобы данные сохранялись между запусками:

```powershell
docker volume create time-tracker-data
docker run --rm -it -v time-tracker-data:/app/data time-tracker-kr5
```

Можно хранить данные прямо в папке проекта:

```powershell
mkdir data
docker run --rm -it -v "${PWD}\data:/app/data" time-tracker-kr5
```

Тогда файлы будут:

```text
KR5/data/tasks.csv
KR5/data/sessions.csv
```

## KR5: как показать тесты

При обычной сборке Docker может использовать кэш, и строка с тестами будет выглядеть так:

```text
CACHED [build 5/5] RUN cmake ... && ctest ...
```

Чтобы точно увидеть запуск тестов:

```powershell
docker build --no-cache --progress=plain --target build -t time-tracker-kr5-test .
```

В конце надо показать:

```text
100% tests passed, 0 tests failed out of 1
```

## Как отвечать на вопросы преподавателя

### Почему проект разделен на `include` и `src`?

В `include` находятся объявления классов, а в `src` - реализации. Это разделяет интерфейс и код работы функций.

### Почему нужен `TaskManager`, если есть `Task`?

`Task` - это одна задача. `TaskManager` управляет списком задач: создает, ищет, архивирует и удаляет.

### Почему нужен `TimeTracker`?

Он отвечает за рабочие сессии: запуск таймера, остановку таймера и хранение истории.

### Почему нужен `Storage`?

Он отделяет хранение данных от логики приложения. Сейчас данные сохраняются в CSV, но при желании можно заменить хранение, почти не меняя остальные классы.

### Почему в KR4 появилась библиотека `time_tracker_lib`?

Чтобы один и тот же код можно было использовать и в основном приложении, и в тестах.

### Что такое Catch2?

Catch2 - библиотека для unit-тестирования C++.

### Что такое CTest?

CTest - инструмент из CMake для запуска тестов.

### Чем unit-тесты отличаются от сценарных?

Unit-тест проверяет отдельную функцию или класс. Сценарный тест проверяет целый процесс работы программы.

### Зачем нужен Docker?

Docker позволяет собрать, протестировать и запустить проект в одинаковом Linux-окружении, независимо от компьютера.

### Зачем нужна многостадийная сборка?

Чтобы инструменты сборки остались только на стадии `build`, а финальный образ содержал только готовую программу.

### Почему тесты запускаются внутри Dockerfile?

Чтобы финальный образ создавался только если проект успешно собрался и все тесты прошли.

### Что делает `ENTRYPOINT`?

Он задает основную команду контейнера. В этом проекте контейнер запускает `time_tracker`.

### Что делает `delete-task`?

Удаляет задачу по `id` и удаляет связанные с ней рабочие сессии, чтобы история не ссылалась на несуществующую задачу.
