# Software Requirements Specification

## Проект

Тайм-трекер - консольное приложение для учета рабочего времени.

ФИО студента: Лобин Александр Ильич

Номер группы: ЭФБО-06-24

## 1. Введение

### 1.1 Цель

Цель документа - описать требования к проекту "Тайм-трекер", определить функции системы, ограничения, пользователей и основные UML-модели, необходимые для дальнейшей реализации приложения на C++.

### 1.2 Область действия

Система предназначена для локального учета рабочего времени по задачам. Приложение позволяет создавать задачи, запускать и останавливать учет времени, сохранять историю сессий и формировать отчеты за выбранный период.

В рамках первой версии не рассматриваются многопользовательский режим, синхронизация с облачными сервисами, мобильное приложение и веб-интерфейс.

### 1.3 Определения и аббревиатуры

- SRS - Software Requirements Specification, спецификация требований к программному обеспечению.
- UML - Unified Modeling Language, язык визуального моделирования.
- Задача - единица работы, по которой ведется учет времени.
- Сессия - период работы по задаче от запуска до остановки таймера.
- Отчет - агрегированная информация о затраченном времени за период.

## 2. Общее описание

### 2.1 Описание продукта

Тайм-трекер представляет собой консольное C++ приложение, работающее локально на компьютере пользователя. Данные сохраняются в файлы, поэтому пользователь может продолжить учет после перезапуска программы.

### 2.2 Основные функции продукта

- создание задач;
- просмотр списка задач;
- запуск таймера по задаче;
- остановка активного таймера;
- просмотр истории сессий;
- формирование отчета за период;
- сохранение и загрузка данных.

### 2.3 Характеристики пользователей

Основной пользователь - студент, разработчик или фрилансер, которому нужно учитывать время выполнения задач. Пользователь умеет запускать консольные приложения и вводить команды в текстовом интерфейсе.

## 3. Детальные требования

### 3.1 Методология сбора требований

Для сбора требований использован подход User Stories. Были выделены основные роли пользователей и типовые сценарии: создание задачи, запуск работы, завершение работы, просмотр результатов и получение отчета. После этого требования классифицированы по иерархии Карла Вигерса: бизнес-требования, пользовательские требования, функциональные требования и нефункциональные требования.

### 3.2 Бизнес-требования

BR-1. Снизить трудозатраты на ручной учет рабочего времени.

BR-2. Повысить прозрачность распределения времени между задачами.

BR-3. Обеспечить возможность быстро сформировать отчет о выполненной работе.

### 3.3 Пользовательские требования

UR-1. Пользователь должен иметь возможность создавать, просматривать и архивировать задачи.

UR-2. Пользователь должен иметь возможность запускать и останавливать таймер.

UR-3. Пользователь должен иметь возможность просматривать историю рабочих сессий.

UR-4. Пользователь должен иметь возможность получать отчет за выбранный период.

UR-5. Пользователь должен иметь возможность продолжить работу с сохраненными данными после перезапуска приложения.

### 3.4 Функциональные требования

FR-1. Система должна создавать задачу с уникальным идентификатором, названием, описанием и статусом.

FR-2. Система должна отображать список активных задач.

FR-3. Система должна запускать рабочую сессию для выбранной задачи.

FR-4. Система должна запрещать одновременный запуск нескольких активных сессий.

FR-5. Система должна завершать активную сессию и сохранять время начала, окончания и длительность.

FR-6. Система должна сохранять задачи и сессии в локальные файлы.

FR-7. Система должна загружать сохраненные данные при запуске.

FR-8. Система должна формировать отчет с суммарным временем по каждой задаче за период.

FR-9. Система должна обрабатывать некорректный ввод без аварийного завершения.

### 3.5 Нефункциональные требования

NFR-1. Приложение должно быть реализовано на C++.

NFR-2. Приложение должно работать в консоли.

NFR-3. Приложение не должно требовать подключения к интернету.

NFR-4. Данные должны храниться локально в текстовом или CSV-формате.

NFR-5. При объеме до 1000 сессий основные команды должны выполняться менее чем за 1 секунду.

NFR-6. Интерфейс должен быть понятным для пользователя без специального обучения.

NFR-7. Исходный код должен быть разделен на логические модули.
